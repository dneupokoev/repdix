# 📘 Проект: repdix (Reporting & Data eXplorer)

## 🎯 1. Цель проекта
Создать универсального Telegram-бота-оркестратора с системой модерации доступа, который принимает вопросы на естественном языке, переводит их в SQL-запросы через LLM, выполняет их в базе данных (MySQL, PostgreSQL, SQLite) и возвращает пользователю **глубокий аналитический ответ**. 

Бот работает в режиме **AI-агента**: он умеет самостоятельно строить цепочки SQL-запросов (Agent Loop), находить скрытые закономерности (например, «почему упали продажи»), показывать процесс своих рассуждений в реальном времени (Chain of Thought) и прерывать выполнение по команде.

## 🛠️ 2. Технологический стек
- **Язык:** Python 3.12.
- **Менеджер зависимостей:** Pipenv.
- **Асинхронность:** `asyncio`, `asyncio.Task` (для фоновых задач и отмены).
- **Telegram:** `aiogram` (v3.x) + `FSMContext` (для интервью при регистрации).
- **LLM:** `openai` (AsyncOpenAI). Основная модель — **DeepSeek V4.1 Flash** (через OpenCode Zen) или локальные аналоги.
- **Базы данных:** `aiomysql` (MySQL), `asyncpg` (PostgreSQL), `aiosqlite` (SQLite).
- **Кэширование:** `redis.asyncio`.
- **Конфигурация:** `python-dotenv` и `PyYAML`.

## 🏗️ 3. Архитектура (Порты и Адаптеры)
Ядро ничего не знает о Telegram. Общение идёт через абстрактные интерфейсы.

```text
repdix/
├── app/
│   ├── main.py                 # точка входа: инициализация сервисов и адаптеров
│   ├── core/                   # бизнес-логика (независима от мессенджера)
│   │   ├── engine.py           # ядро: Agent Loop, tool_calls, управление сессией
│   │   ├── session.py          # SessionState (история, lock, current_task)
│   │   ├── db_manager.py       # пулы соединений, безопасные запросы к целевой БД
│   │   ├── user_manager.py     # управление доступом (hot-reload users.yaml)
│   │   ├── llm_client.py       # клиент LLM (temperature=0.3, tool_choice)
│   │   ├── cache_manager.py    # Redis (история диалогов)
│   │   ├── rbac_guard.py       # проверка прав доступа к таблицам и полям
│   │   └── validator.py        # SQL-валидатор (только SELECT)
│   └── interfaces/             # адаптеры мессенджеров
│       ├── base.py             # ChatMessage (с колбэком статуса), ChatResponse
│       ├── telegram_adapter.py # Telegram (aiogram), FSM-регистрация, статусы, /stop
│       └── cli_adapter.py      # Консольный интерфейс (отладка)
├── config/
│   ├── databases.yaml          # шаблоны подключений к целевым БД (${VAR} из .env)
│   ├── models.yaml             # шаблоны моделей LLM
│   ├── relations.yaml          # описание связей (для JOIN)
│   ├── templates.yaml          # детерминированные шаблоны (топы/рейтинги)
│   ├── users.yaml              # список пользователей, ролей и статусов (НЕ КОММИТИТЬ)
│   ├── roles.yaml              # описание ролей и прав (RBAC)
│   └── help.md                 # справка /help
├── data/                       # локальные данные (опционально)
├── tests/                      # pytest
├── .env                        # секреты (НЕ КОММИТИТЬ)
└── .gitignore
```

## 🗄️ 4. Работа с базами данных
- **Шаблоны в `config/databases.yaml`**: реальные значения подставляются из `.env` через `${VAR}`.
- **Read-only на уровне БД обязателен.** Валидатор SQL — лишь дополнительный барьер.
- **Таймауты:** `SQL_QUERY_TIMEOUT` (по умолчанию 15 секунд) прерывает тяжелые запросы на уровне БД.

## 🧠 5. Работа с моделями и AI-Агент

### 5.1. Agent Loop (Цикл агента)
В `engine.py` реализован цикл `while step < max_steps` (до 5 шагов). Модель может: запросить список таблиц, изучить структуру, сделать запрос за два периода, сравнить результаты и написать бизнес-вывод.
**Важно:** В цикле сообщения модели обязательно передаются с ролью `"tool"` и `tool_call_id`, иначе DeepSeek вернёт ошибку 400.

### 5.2. Chain of Thought (Прозрачность)
Перед каждым вызовом инструмента модель пишет краткое пояснение. 
**Как это работает:** В `ChatMessage` есть `status_callback`. `telegram_adapter.py` отправляет эти статусы пользователю (вида `🤖 Сейчас посмотрю структуру...`). В `engine.py` текст перехватывается и отправляется через колбэк. Статусы автоматически обрезаются до 80 символов, чтобы не засорять чат.

### 5.3. Инструменты модели (Tool Calling)
- `execute_sql` — для сложных аналитических запросов.
- `get_relations` — узнать связи таблиц.
- `execute_template` — выполнить быстрый запрос из `config/templates.yaml`.
- **⚠️ Важно:** Мы **отказались** от тяжелого `get_table_schema` (он возвращал гигантский JSON, переполнял контекст). В `base_prompt` велено использовать `SHOW COLUMNS` через `execute_sql`. **Не возвращайте `get_table_schema` обратно!**

### 5.4. Управление историей и прерывание
- История хранится в `SessionState` и дублируется в Redis (TTL 24 часа, `max_history = 10`).
- **Как работает `/stop`:** В `telegram_adapter.py` обработка запускается в `asyncio.create_task`. Ссылка сохраняется в `SessionState.current_task`. Команда `/stop` вызывает `state.current_task.cancel()`, что прерывает все ожидания SQL и LLM.

## 🛡️ 6. Управление доступом (Модерация и RBAC)
Доступ к боту строго контролируется:
1. **Администраторы** (указаны в `ADMIN_USERS` в `.env` или имеют роль `admin` в `users.yaml`) имеют доступ ко всему.
2. **Обычные пользователи** при первом `/start` проходят интервью (ФИО, Отдел, Цель). Данные сохраняются в `config/users.yaml` (с флагом `is_active: false`). Пока админ не одобрит заявку, бот не пустит пользователя к LLM. **Файл перечитывается «на лету» (hot-reload) при каждом запросе, перезапуск не нужен.**
3. **RBAC (Role-Based Access Control):** В `config/roles.yaml` описываются роли (например, `sales_manager`) и права на таблицы/поля. `RBACGuard` физически блокирует запросы к запрещенным таблицам и полям, даже если LLM сгенерирует такой SQL.
4. **Статусы:** `is_active: true` (доступ), `is_active: false` (бан/ожидание).

## 🛠️ 7. Служебные команды
| Команда | Описание |
|---|---|
| `/stop` | **Прервать текущий анализ** (отменяет фоновую задачу). |
| `/help` | Справка. |
| `/db`, `/db <name>` | Текущая БД / выбор новой. |
| `/model`, `/model <name>` | Текущая модель / переключение. |
| `/sql <query>` | Выполнить SQL вручную (только для одобренных). |
| `/history`, `/compact`, `/clear`, `/tokens` | Управление контекстом. |

## ⚙️ 8. Инструкция по настройке

### 8.1. Локальная разработка
1. Установите Python 3.12 и Pipenv.
2. `pipenv install --dev`.
3. Создайте `.env` и `config/*.yaml`.
4. Запустите Redis.
5. Запустите `./prj_start.sh`.

### 8.2. Файл `.env` (пример)
```env
# Telegram
TELEGRAM_TOKEN=ваш_токен
ADAPTER=telegram

# Администраторы (ID через запятую). Им не нужна регистрация.
ADMIN_USERS=123456789,987654321

# LLM (DeepSeek)
LLM_TOOL_URL=https://opencode.ai/inference/openai/v1
LLM_TOOL_TOKEN=sk-ваш_ключ
LLM_TOOL_MODEL=deepseek-v4.1-flash
DEFAULT_MODEL=tool_calling_model

# Базы данных
DB_MAIN_HOST=...
DB_MAIN_PASSWORD=...

# Redis
REDIS_HOST=localhost
REDIS_PORT=6379
REDIS_PASSWORD=пароль

# Лимиты
SQL_QUERY_TIMEOUT=15
MAX_ROWS_IN_RESPONSE=100
MAX_MESSAGE_LENGTH=4000
```

## ⚠️ 9. Ограничения и известные проблемы
- **Одновременные запросы:** `asyncio.Lock` на каждого пользователя. Разные пользователи работают параллельно, один — последовательно.
- **Время ответа:** На сложный вопрос бот может сделать 5–10 SQL-запросов и потратить 30–60 секунд. Используйте `/stop`, если передумали.
- **Стоимость LLM:** Сложный анализ может стоить несколько центов. Бот автоматически ограничивает выгрузку строк (`LIMIT 10` для транскрибаций, `LIMIT 100` для остальных), чтобы не переполнять контекст.
- **Файлы конфигурации:** `config/users.yaml` содержит персональные данные (ФИО). **Обязательно** добавьте `config/users.yaml` и `.env` в `.gitignore`, чтобы не закоммитить их в публичный репозиторий.
