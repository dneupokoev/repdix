# app/core/rbac_guard.py

Версия файла: `261029.07`

## Назначение

Модуль реализует RBAC-гард для проверки SQL-запросов на соответствие ролям пользователя из `config/roles.yaml`, а также предварительную блокировку технических таблиц и колонок.

Основные принципы:

- доступ к таблице проверяется по полному имени `schema.table`;
- правило без схемы не матчится к qualified-имени, если схема уже известна; это закрывает обход RBAC через смену схемы;
- если в SQL не указана схема, используется `default_schema`;
- `SELECT *` запрещается, если у таблицы есть `excluded_columns`, чтобы исключённые поля не утекли через звёздочку;
- `SELECT *` также может запрещаться по таблицам с техническими колонками, если передан `technical_columns_getter`;
- единственный парсер SQL — `sqlglot` с диалектом `mysql`;
- технические таблицы и колонки блокируются до проверки RBAC-правил, чтобы wildcard-правило `*` не открывало к ним доступ;
- проверка безопасности SQL-запроса как такового выполняется отдельно, в `validator.py`; данный модуль проверяет именно RBAC-права и технические ограничения.

## Класс `RBACGuard`

Проверяет SQL-запросы на соответствие ролям из `config/roles.yaml`.

### `__init__(roles_config_path: str = "config/roles.yaml", technical_columns_getter=None)`

Создаёт экземпляр гарда.

Аргументы:

- `roles_config_path` — путь к YAML-файлу с ролями. По умолчанию `config/roles.yaml`;
- `technical_columns_getter` — необязательный синхронный callable для получения списка/набора технических колонок по имени таблицы. Используется для запрета `SELECT *` по таблицам с техническими колонками до проверки RBAC-правил.

Внутреннее состояние:

- `_config` — загруженный словарь ролей;
- `_mtime` — время последнего изменения файла конфигурации для hot-reload;
- `_technical_columns_getter` — переданный getter технических колонок.

### `_load_config() -> None`

Загружает конфиг ролей с поддержкой hot-reload.

Поведение:

- если файл не существует, метод просто возвращает управление;
- если `mtime` файла больше сохранённого, конфиг перечитывается;
- из YAML берётся секция `roles`;
- при ошибке чтения пишется лог, предыдущий конфиг сохраняется;
- успешная загрузка обновляет `_mtime`.

### `_collect_rules(user_roles: list[str]) -> dict[str, dict]`

Собирает правила доступа для набора ролей.

Аргументы:

- `user_roles` — список ролей пользователя.

Возвращает словарь вида:

- ключ — имя таблицы в нижнем регистре: `schema.table`, короткое имя, `schema.*` или `*`;
- значение — словарь:
  - `allowed` — множество явно разрешённых колонок;
  - `excluded` — множество запрещённых колонок;
  - `has_wildcard` — `True`, если `allowed_columns == "*"`.

Особенности:

- ключи нормализуются к нижнему регистру;
- правила из нескольких ролей объединяются;
- правило без схемы трактуется как короткое имя и не даёт доступа к одноимённой таблице в другой схеме;
- если описание таблицы в роли не является словарём, оно трактуется как пустое.

### `get_allowed_schema_for_llm(user_roles: list[str]) -> str`

Формирует краткое текстовое описание доступных таблиц для промпта LLM.

Аргументы:

- `user_roles` — список ролей пользователя.

Возвращает:

- строку с перечнем доступных таблиц и полей;
- `"У вас нет доступа ни к одной таблице."`, если правил нет.

Примечание: `engine._get_db_schema()` может строить более подробное описание с полями из реальной БД. Данный метод оставлен для обратной совместимости и для случаев, когда нет доступа к `DBManager`.

### `get_allowed_tables(user_roles: list[str], schemas: list[str], default_schema: str = "", all_tables: list[str] | None = None) -> set[str]`

Возвращает множество разрешённых таблиц в нижнем регистре.

Аргументы:

- `user_roles` — список ролей пользователя;
- `schemas` — список доступных схем; в текущей реализации параметр не используется, но сохранён в сигнатуре для совместимости и документации;
- `default_schema` — схема для нормализации коротких ключей;
- `all_tables` — реальный список таблиц из БД в формате `schema.table`; нужен для разворачивания правил `schema.*` в конкретные таблицы.

Поведение:

- wildcard-правило `*` возвращается как `{"*"}`; вызывающий код сам разворачивает его во все схемы;
- qualified-ключи `schema.table` возвращаются как есть;
- короткие ключи при наличии `default_schema` нормализуются к `default_schema.key`;
- ключ `schema.*` разворачивается в конкретные fully-qualified имена только если передан `all_tables`;
- без `all_tables` ключ `schema.*` возвращается как есть для обратной совместимости;
- если `default_schema` не задан, короткий ключ возвращается как есть.

### `get_allowed_schemas(user_roles: list[str], available_schemas: list[str], default_schema: str = "") -> set[str]`

Возвращает множество схем, к которым у ролей есть доступ.

Аргументы:

- `user_roles` — список ролей пользователя;
- `available_schemas` — список реально доступных схем;
- `default_schema` — схема для коротких ключей.

Поведение:

- wildcard-правило `*` даёт доступ ко всем `available_schemas`;
- qualified-ключ `schema.table` добавляет схему `schema`, если она есть в `available_schemas`;
- ключ `schema.*` также добавляет схему `schema`, если она есть в `available_schemas`;
- короткий ключ добавляет `default_schema`, только если она есть в `available_schemas`;
- если `default_schema` не задан, короткие ключи не добавляют схем.

### `validate_sql(sql: str, user_roles: list[str], default_schema: str = "") -> tuple[bool, str]`

Основная проверка SQL на соответствие правам пользователя и техническим ограничениям.

Аргументы:

- `sql` — SQL-запрос;
- `user_roles` — список ролей пользователя;
- `default_schema` — схема, которая подставляется, если в SQL схема не указана.

Возвращает:

- `(True, sql)` — если запрос разрешён;
- `(False, reason)` — если запрос запрещён.

Порядок проверки:

1. SQL парсится через `sqlglot.parse_one(sql, read="mysql")`.
2. При ошибке парсинга или пустом результате доступ запрещается.
3. Проверяются технические таблицы из `exp.Table`; при совпадении с техническим именем доступ запрещается.
4. Проверяются технические колонки из `exp.Column`; звёздочки пропускаются, остальные колонки проверяются по полному или короткому имени.
5. Если задан `technical_columns_getter` и в запросе есть любой `exp.Star`, проверяется наличие технических колонок у таблиц запроса; при наличии таких колонок `SELECT *` запрещается.
6. Загружается конфиг и собираются RBAC-правила.
7. Если правил нет — доступ запрещается.
8. Проверяются все таблицы из `exp.Table`; для каждой ищется правило через `_match_table_rule`.
9. Проверяются звёздочки `exp.Star`, в том числе `SELECT *` и `t.*`.
10. Проверяются колонки `exp.Column`.
11. При успехе возвращается исходный SQL.

Особенности проверки технических объектов:

- технические таблицы и колонки блокируются до RBAC-правил, чтобы правило `*` не открывало к ним доступ;
- для таблиц проверяется qualified-имя, включая схему и таблицу; `_table_qualified_name()` при этом не подставляет `default_schema`;
- для колонок проверяется полное имя `table.column`, если колонка квалифицирована, иначе короткое имя;
- при проверке `SELECT *` getter технических колонок вызывается как для qualified-имени таблицы, так и для короткого имени;
- getter синхронный; по комментарию в коде в `engine` может передаваться `None`, так как `db_manager` асинхронный, а реальная страховка выполняется пост-фильтрацией результата в `engine`.

Особенности проверки таблиц:

- имя таблицы и схемы приводится к нижнему регистру;
- если схема не указана, используется `default_schema`;
- для каждой таблицы ищется правило через `_match_table_rule`;
- если правило не найдено — доступ запрещается;
- строится `table_rule_map`, где правило доступно и по qualified-имени, и по короткому имени для случаев с неквалифицированными колонками.

Особенности проверки `SELECT *`:

- если у таблицы есть `excluded_columns`, `SELECT *` запрещается;
- для `t.*` проверяется правило конкретной таблицы;
- для неквалифицированной звёздочки проверяются все таблицы запроса;
- дополнительно `SELECT *` может быть запрещён при наличии технических колонок, если задан `technical_columns_getter`;
- если скрытых полей и технических ограничений нет, звёздочка допускается.

Особенности проверки колонок:

- исключённые поля запрещены всегда;
- квалифицированная колонка проверяется строго по правилу своей таблицы;
- если у таблицы нет wildcard, колонка должна быть в `allowed`;
- неквалифицированная колонка проверяется по всем таблицам запроса;
- если колонка есть в `excluded` хотя бы одной таблицы-кандидата — доступ запрещается;
- колонка должна быть разрешена хотя бы в одной таблице запроса.

### `_table_qualified_name(table: exp.Table) -> str`

Статический метод. Возвращает qualified-имя таблицы `schema.table` в нижнем регистре или короткое имя, если схема отсутствует. `default_schema` здесь не подставляется.

### `_match_table_rule(tbl_name: str, schema_name: str, rules: dict[str, dict]) -> dict | None`

Ищет правило для таблицы.

Аргументы:

- `tbl_name` — имя таблицы;
- `schema_name` — имя схемы;
- `rules` — собранные правила.

Порядок поиска:

1. Точное qualified-совпадение `schema.table`.
2. Wildcard-правило `*` для всех таблиц.
3. Wildcard схемы `schema.*` для всех таблиц указанной схемы, если схема известна.
4. Короткое имя таблицы — только если `schema_name` пуст.

Если правило не найдено, возвращается `None`.

## Использование в проекте

По docstring, комментариям и публичным методам модуль предназначен для использования другими частями проекта:

- `validate_sql()` — вызывается перед выполнением SQL для проверки RBAC-прав пользователя и технических ограничений;
- `get_allowed_schema_for_llm()` — используется для построения текстового описания доступных таблиц для промпта LLM;
- `get_allowed_tables()` — используется для получения множества разрешённых таблиц; поддерживает нормализацию коротких ключей и разворачивание `schema.*` при передаче `all_tables`;
- `get_allowed_schemas()` — используется для получения множества схем, доступных ролям;
- `engine._get_db_schema()` может использовать более подробное описание схемы из БД, но `get_allowed_schema_for_llm()` оставлен для обратной совместимости;
- `is_technical_qualified()` из `app.core.technical_filter` используется для блокировки технических таблиц и колонок до применения RBAC-правил;
- проверка безопасности SQL выполняется отдельно в `validator.py`.

Изолированно по файлу видны только импорт `app.core.technical_filter.is_technical_qualified` и упоминания `engine`, `DBManager`, `validator.py` в docstring/комментариях. Конкретные места вызова из кода проекта по этому файлу не определяются.

## Ограничения и заметки

- Модуль проверяет RBAC и технические ограничения, а не общую безопасность SQL.
- Парсинг выполняется только диалектом `mysql`.
- При ошибке парсинга доступ запрещается.
- Правило без схемы не даёт доступа к qualified-имени.
- Если задан `default_schema`, короткие правила таблиц не будут использованы для таблиц без явной схемы, так как схема уже подставлена.
- `SELECT *` запрещается при наличии `excluded_columns`; дополнительно он может запрещаться при наличии технических колонок и заданном `technical_columns_getter`. Если скрытых полей и технических ограничений нет, звёздочка допускается.
- Технические таблицы и колонки блокируются до RBAC-правил, включая случай wildcard-правила `*`.
- Hot-reload срабатывает при увеличении `mtime` файла конфигурации.
- При отсутствии или ошибке чтения `roles.yaml` предыдущий конфиг не очищается.
- Если конфиг пуст или у пользователя нет ролей с таблицами, доступ запрещается.
- `technical_columns_getter` синхронный; при `None` проверка `SELECT *` по техническим колонкам в этом модуле не выполняется, а ответственность переносится на пост-фильтрацию результата в `engine`.
- `get_allowed_tables()` возвращает `set[str]`, а не список.
- В `get_allowed_tables()` параметр `schemas` в текущей реализации не используется; wildcard `*` возвращается как `{"*"}` и разворачивается вызывающим кодом.
- Правило `schema.*` в `get_allowed_tables()` разворачивается в конкретные таблицы только при передаче `all_tables`; без него ключ возвращается как есть.
- `get_allowed_schemas()` для коротких ключей использует только `default_schema`, если она входит в `available_schemas`.
- Техническая проверка таблиц в `validate_sql()` использует имя из SQL через `_table_qualified_name()` и не подставляет `default_schema` на этом этапе.
