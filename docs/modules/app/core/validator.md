# app/core/validator.py

**Версия файла:** `dv_file_version = '261030.01'`. В текущем файле нет упоминаний версии `261030.02`; если такие сведения встречались в предыдущей документации, они не соответствуют данному коду.

## Назначение

Модуль содержит валидатор SQL-запросов для предварительной проверки безопасности. Он пропускает только запросы, начинающиеся с `SELECT` или `WITH`, блокирует DML/DDL/административные конструкции, опасные паттерны, множественные запросы, нулевые байты и слишком длинный SQL.

Валидатор использует `sqlglot` для fail-closed-разбора SQL с диалектом `mysql`: любая ошибка разбора приводит к отказу. При этом модуль остаётся предварительным фильтром, а не полноценной заменой ограничениям прав БД, параметризации запросов и другим мерам безопасности.

Функция `_strip_comments_for_check()` реализована посимвольным сканером: комментарии `--` (в том числе без обязательного пробела после), `#` и `/* */` вырезаются только вне строковых литералов. Учитываются экранирование (`\'`, `\"`) и удвоение кавычек (`''`, `""`). Это снижает число ложных блокировок легитимных запросов и сохраняет блокировку множественных запросов.

Дополнительно модуль содержит `strip_sql_comments()` — удаление комментариев для передачи SQL в БД, а не только для проверки.

## Публичный API

Классов нет.

### `validate_sql(sql: str) -> tuple[bool, str]`

Проверяет SQL-запрос.

Аргументы:
- `sql` — строка SQL-запроса.

Возвращает:
- `(True, "")`, если запрос прошёл проверки;
- `(False, reason)`, если запрос отклонён. `reason` — краткая причина отклонения на английском.

Порядок проверок:
1. Пустой или состоящий из пробелов SQL отклоняется.
2. SQL длиннее `100_000` символов отклоняется.
3. Наличие нулевого байта `\x00` отклоняется.
4. Удаляется завершающая `;` с хвостовыми пробелами через `re.sub(r";\s*$", "", sql.strip())`.
5. Если после очистки строка пустая — отказ.
6. Выполняется `sqlglot.parse(cleaned, read="mysql")`:
   - исключение при разборе — отказ;
   - отсутствие statement — отказ;
   - больше одного statement — отказ.
7. Комментарии вырезаются только для проверки через `_strip_comments_for_check()`: `/* ... */`, `-- ...`, `# ...` вне строковых литералов.
8. Если после удаления комментариев строка пустая — отказ.
9. Выполняется страховочная проверка `_has_statement_separator(check_sql)`: наличие `;` вне строковых литералов после удаления комментариев даёт отказ `multiple statements`.
10. Запрос должен начинаться с `SELECT` или `WITH` без учёта регистра.
11. Проверяются запрещённые ключевые слова как отдельные токены.
12. Проверяются опасные regex-паттерны.

Проверка вида `";" in cleaned` до `sqlglot.parse` больше не используется: она давала ложные срабатывания на `;` внутри комментариев. Множественные запросы в первую очередь определяются через `sqlglot.parse`, дополнительно — через `_has_statement_separator()` после удаления комментариев.

### `validate_sql_verbose(sql: str) -> tuple[bool, str, str]`

Расширенная версия `validate_sql`.

Аргументы:
- `sql` — строка SQL-запроса.

Возвращает:
- `(is_valid, reason, cleaned_sql)`, где `cleaned_sql` — `sql.strip()` с удалённой завершающей `;` и хвостовыми пробелами.

`cleaned_sql` вычисляется даже при неуспешной проверке. Комментарии в `cleaned_sql` не удаляются — удаляется только завершающая `;`.

### `strip_sql_comments(sql: str) -> str`

Удаляет SQL-комментарии вне строковых литералов для передачи SQL в БД.

Аргументы:
- `sql` — строка SQL-запроса.

Возвращает:
- SQL без комментариев `--`, `#`, `/* */` вне литералов, с удалёнными ведущими и хвостовыми пробелами;
- исходную строку, если после вырезания комментариев не осталось значимого текста.

Сохраняет строковые литералы, экранирование и удвоение кавычек. Предназначена для выполнения, в отличие от `_strip_comments_for_check()`.

### `log_violation(user_id: str, sql: str, reason: str) -> None`

Записывает событие нарушения SQL-безопасности.

Аргументы:
- `user_id` — идентификатор пользователя;
- `sql` — исходный SQL;
- `reason` — причина отклонения.

Поведение:
- SQL санитизируется для лога: обрезается до 1000 символов, переводы строк заменяются на литералы `\\n` и `\\r`;
- если у логгера `security` есть обработчики, запись идёт через `logging.getLogger("security")`;
- иначе используется fallback: создаётся каталог `logs` и выполняется дозапись в `logs/security.log`;
- дублирование в консоль/основной лог выполняется через `logging.getLogger(__name__).warning(...)`.

## Внутренние функции

### `_strip_comments_for_check(sql: str) -> str`

Удаляет SQL-комментарии только для проверки, не для выполнения:
- `/* ... */`;
- `-- ...`;
- `# ...`.

Удаление выполняется посимвольным сканером только вне строковых литералов `'...'` и `"..."`. Внутри литералов учитываются экранирование обратным слешем и удвоение кавычек. Незакрытый строковый литерал обрабатывается fail-closed: комментарий не вырезается, поэтому запрещённые конструкции, если они есть, остаются видимыми для проверок. Вложенные комментарии не поддерживаются — многострочный комментарий завершается на первом `*/`. На месте комментария оставляется пробел.

### `_has_statement_separator(sql: str) -> bool`

Возвращает `True`, если `;` встречается вне строковых литералов. Ожидает SQL уже без комментариев. Учитывает экранирование (`\'`, `\"`) и удвоение кавычек (`''`, `""`). Используется как дополнительная страховка после `sqlglot.parse`: например, для `SELECT 1; -- DROP` запрос отклоняется как `multiple statements`, а `SELECT ';' AS x` — нет.

## Константы

- `FORBIDDEN_KEYWORDS` — список запрещённых ключевых слов. Проверяются как отдельные токены без учёта регистра. Включает `INSERT`, `UPDATE`, `DELETE`, `DROP`, `ALTER`, `TRUNCATE`, `REPLACE`, `CREATE`, `GRANT`, `REVOKE`, `MERGE`, `ATTACH`, `DETACH`, `PRAGMA`, `VACUUM`, `ANALYZE`, `REINDEX`, `FLUSH`, `KILL`, `SHUTDOWN`, `OPTIMIZE`, `REPAIR`, `HANDLER`, `EXEC`, `EXECUTE`, `CALL`, `PREPARE`, `DEALLOCATE`, `COPY`, `LISTEN`, `NOTIFY`, `UNLISTEN`, `LOAD`.
- `DANGEROUS_PATTERNS` — список regex-паттернов для опасных конструкций: `INTO OUTFILE`, `INTO DUMPFILE`, `INTO @var`, `FOR UPDATE`, `FOR SHARE`, `LOCK IN SHARE MODE`, `LOAD_FILE(...)`, `PROCEDURE ...`, `SLEEP(...)`, `BENCHMARK(...)`, `WAITFOR DELAY`, `PG_SLEEP(...)`, `DBLINK(...)`, `COPY ... FROM PROGRAM`, `LOAD DATA INFILE`, `SET GLOBAL/SESSION/@@`.
- `_MAX_SQL_LENGTH = 100_000` — максимальная длина SQL в символах.
- `dv_file_version = '261030.01'` — версия файла в коде.
- `_security_logger = logging.getLogger("security")` — логгер security-событий.
- `_app_logger = logging.getLogger(__name__)` — логгер модуля для обычных предупреждений.

## Использование в проекте

В изолированном файле не видно фактических импортов этого модуля другими модулями и нет вызовов извне. Ожидаемые точки интеграции:

- другие модули импортируют `validate_sql()` или `validate_sql_verbose()` из `app.core.validator` и вызывают их перед выполнением SQL;
- при отказе вызывается `log_violation()` для записи события безопасности;
- `strip_sql_comments()` может использоваться перед передачей SQL в БД, если нужно удалить комментарии, сохранив строковые литералы;
- согласно докстрингу, логгер `security` настраивается в `main.py._setup_logging()`, например через `RotatingFileHandler`;
- согласно докстрингу, `validate_sql_verbose()` может использоваться движком/engine, чтобы получить очищенный SQL без завершающей `;`.

## Ограничения и замечания

- Это предварительный фильтр, а не полноценная система безопасности SQL.
- `sqlglot` используется с `read="mysql"` и fail-closed: ошибка разбора отклоняет запрос. Это может отклонять валидный, но не поддержанный парсером синтаксис.
- Проверка `;` выполняется после удаления комментариев и вне строковых литералов. `;` внутри комментариев или литералов не считается разделителем. При этом `SELECT 1; -- DROP` отклоняется как multiple statements, а `SELECT 1 -- ; DROP` — нет.
- Строковые литералы не исключаются из проверки запрещённых слов и опасных паттернов: запрещённые слова внутри строк также могут привести к отказу.
- `validate_sql_verbose()` не удаляет комментарии из возвращаемого SQL, а только завершающую `;`.
- `strip_sql_comments()` удаляет комментарии для выполнения, но может менять пробелы и форматирование SQL.
- Fallback-логирование в `logs/security.log` выполняется без ротации. Ротацию обеспечивает внешняя настройка логгера `security`.
- Отдельного запрета на `SET` в `FORBIDDEN_KEYWORDS` нет. Блокируются только конструкции вида `SET GLOBAL`, `SET SESSION`, `SET @@` через `DANGEROUS_PATTERNS`.
- `_strip_comments_for_check()` не является полноценным SQL-лексером: не поддерживает вложенные комментарии и все особенности диалектов SQL. При этом он корректно не вырезает комментарии внутри строковых литералов и учитывает экранирование и удвоение кавычек.
- `_has_statement_separator()` не удаляет комментарии самостоятельно и корректен только для SQL, уже обработанного `_strip_comments_for_check()`.
- В коде указана версия `dv_file_version = '261030.01'`; упоминаний версии `261030.02` в текущем файле нет. Если предыдущая документация ссылалась на `261030.02`, это расхождение с данным кодом.
